# SignUnder

Hosted service that gets a company signing AI-generated content under its own name (C2PA conformance, signing, watermarking, verification, rule packs). The folder is still called `Cereal`, the old placeholder name.

## Documents

- This repository is public (Apache-2.0). Anything about customers, prospects, pricing, strategy or marketing belongs in the private repository `AivaStack/signunder-private`, checked out at `../signunder-private`, never here; that includes issue text, commit messages and workflow output.
- `docs/ARCHITECTURE.md` is the architecture, the testing approach and, in its section 3, the log of technical decisions.
- `../signunder-private/SIGNUNDER.md` is the product, market, business and build plan. Its section 7 logs product and business decisions and section 8 holds the open questions.
- `docs/adr/` holds one record per technical decision, numbered `NNNN-short-title.md`.
- When a decision makes either of them, or this file, out of date, propose the specific change with a Yes/No question at the next checkpoint. Do not edit them silently and do not wait to be asked.
- Both mark anything not read from a primary source as UNVERIFIED or *from memory*. Keep to that.
- The search and AI-search marketing plan and its work list are in `../signunder-private/marketing/`. Blog and reference content lives in `content/` as Markdown and is pulled into `signunder-web` at build. Law content follows the same rule: cite the primary source and the date read, or mark it UNVERIFIED.

## Layout

- `src/Signunder.Api`, `Signunder.Core`, `Signunder.Rules`, `Signunder.Sdk`: .NET 10 (version pinned in `global.json`, shared settings in `Directory.Build.props`, warnings are errors).
- `src/sign-sidecar`: Rust, wraps c2pa-rs, talks gRPC to the API.
- `src/signunder-py`: the Python SDK, published to PyPI as `signunder` (Apache-2.0) by pushing a tag `python-vX.Y.Z` that matches `pyproject.toml`; trusted publishing, no token. Live test against staging: `SIGNUNDER_LIVE=1 SIGNUNDER_API_KEY=… uv run pytest`.
- `src/wm-worker`: Python, managed with uv. TrustMark watermarking and PDQ fingerprinting over gRPC; its generated gRPC code (`src/wm_worker/pb`) is not committed, `uv run ./genproto.sh` makes it.
- `proto/signunder/sign/v1/sign.proto`: the API-to-sidecar contract.
- `proto/signunder/wm/v1/wm.proto`: the API-to-watermark-worker contract.
- `tests/`: xUnit projects for Core, Rules and the API (`Signunder.Api.Tests` hosts the API against Postgres in a container with a stand-in sidecar); `tests/conformance` holds the sample generator; `tests/robustness` holds the watermark survival suite, run from the worker's environment; the other folders are placeholders.
- `tools/approve-identity.py`: approves a company's name for the CAWG identity assertion and issues its certificate with the sidecar's `identity-ca` binary; `deploy/identity-ca/root.pem` is the Identity CA's root certificate (ADR 0014).
- `tools/security/`: the vulnerability scan (`scan.sh`) and the check that `.trivyignore.yaml` defers nothing beyond 90 days (ADR 0009).
- `deploy/docker-compose.yml`: local stack.
- `deploy/fly/`: Fly.io configurations for staging (ADR 0012); deploy from the repository root. The API's browser callers come from `Website:AllowedOrigins`, and dashboard sign-in tokens from `SupabaseAuth:Issuer` (ADR 0013). `tools/supabase.sh` runs the Supabase CLI with this project's own token from `.env`, leaving the machine's global Supabase login alone.
- `tools/rules-watch/`: the source watch. Its snapshots (the visible text of third-party pages, for diffs) live in `../signunder-private/rules-watch/snapshots`, and the weekly run is a workflow there. `manual.json` lists the sources no script can read, to check by hand.
- `content/rules/`: generated by `make rules` from `src/Signunder.Rules/packs` and the hand-written `scenarios.json`; the website serves the packs at `/rules/*.json` and the answers at `/checker/{slug}`.
- `content/`: blog posts and reference pages (law, platforms, labels, guides, compare) as Markdown, with templates in `content/_templates/`. Published by `signunder-web`, never rendered from here.
- The web front end (Next.js, shadcn/ui, Zippay template) lives in a separate private repo, `signunder-web`. Never copy template code into this repo: it is licensed, and this repo is public.

## Commands

```
make build   # dotnet build + cargo build
make test    # dotnet test + cargo test + the worker's pytest (the API tests start Postgres in Docker)
make test-kms  # sidecar tests that sign through the local-kms emulator (needs Docker)
make test-gcp  # sign through a real Cloud KMS key: SIGNUNDER_TEST_GCP_KEY=projects/.../cryptoKeyVersions/1
make robustness  # watermark and fingerprint survival table, then its assertions
make rules   # publish the rule packs and the checker's common answers into content/rules (review the diff; tests fail when stale)
make watch   # check the rule packs' primary sources for changes (weekly in the private repo's CI, opening a rules-watch issue there); make watch-accept after review
make fmt     # dotnet format + cargo fmt + ruff format
make up      # build and start the local stack in Docker
make down
make sample  # with the stack up: sign the fixtures into docs/conformance/samples
make conformance  # run the C2PA program's asset rubric over the samples
make scan    # Trivy: lockfiles and the three service images (ADR 0009)
```

Toolchains are listed in the `Brewfile`. Install the missing formulae one by one (`brew install rustup protobuf`, then `rustup default stable`) rather than running `brew bundle`, which installs the `dotnet-sdk` cask over a dotnet that came from elsewhere. Homebrew's rustup is keg-only: `cargo` needs `/opt/homebrew/opt/rustup/bin` on PATH.

## Hosting

Vercel for the web front end, Supabase (EU) for Postgres, auth, storage and the queue, Fly.io (Frankfurt) for the API, sidecar and worker containers, Google Cloud KMS (HSM, Frankfurt) for signing keys; no AWS account (ADR 0011). See ADRs 0002 and 0011.

Monitoring: Better Stack's free plan pings signunder.com, `/verify` and the staging API's `/healthz` (never `/readyz`: the sidecar sleeps when idle), alerting Eoin by email; a workflow in the private repo signs and verifies an image on staging every six hours and opens an `uptime` issue on failure. Upgrade once there are paying customers. Companies waiting for their name to be approved (ADR 0014) appear in the private repo's `identity-review` issue, refreshed daily; approve with `tools/approve-identity.py SLUG`.
